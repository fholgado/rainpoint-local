# Stock association persistence, rejoin, and sequence consumers

2026-09-28; offline analysis of retained ESP32-S3 hub firmware **1.1.1040**.
No device, RF, cloud, deployment, or runtime-source changes. This note describes
hub behavior, not the sensor/valve firmware's retention or acceptance rules.
Work status remains in [the roadmap](../PROJECT_ROADMAP.md).

## Findings

- The hub saves an association's **52-byte prefix**, not its full 184-byte
  runtime record. Address, device identity, RF selector, model and reported
  software version are in that prefix; online deadlines and allocated runtime
  state are outside it.
- In the traced controller path, native `01` creates a pending candidate;
  native `02` promotes it to persistent storage. A visible pairing response
  alone does not prove that promotion occurred.
- A known-device native `01` reuses the existing address and nonzero selector.
  It can update the reported software version without resetting the separate
  association/configuration version to one.
- Ordinary offline handling is not the same as deletion. There is, however,
  a separate timed **platform-enrollment reconciliation** path that can delete
  an incompletely admitted association.
- Two additional direct consumers of the shared sequence generator are a
  gated OOK/time transmission and native `75` gateway-property response.
  Neither is evidence of a reset or a valve counter-synchronization command.

## Storage boundaries

Configuration dispatcher `4201DF80` routes slot **4** to `4201DC70`.
The slot descriptor specifies blob type **9**, length **52**, and runtime
stride **184**. The handler compares the first 52 bytes before deciding
whether to write; it then copies the complete 184-byte record in RAM.
Independent ESP32-S3 decoding confirms the compare length at `4201DF0C`,
KV-set call at `4201DF26`, and RAM-copy length at `4201DF33`.

| Record offset, decimal | Qualified meaning | Within persisted prefix? |
| --- | --- | --- |
| `+0` | Assigned address | Yes |
| `+1..12` | Formatted device-identity buffer | Yes |
| `+13` | Device class | Yes |
| `+14` | Device-reported software version | Yes |
| `+27` | RF selector | Yes |
| `+28` | Port count | Yes |
| `+30..31` | Model-derived heartbeat/offline settings | Yes |
| `+32..35` | Field tested by the migration/reconnection branch | Yes; full meaning not established |
| `+40..45` | Six-byte identity used by the BLE predicate | Yes |
| `+46..47` | Model code | Yes |
| `+61` | Runtime online state | No |
| `+64..71` | Runtime offline deadline | No |
| `+84`, `+100`, `+120..144` | Model/port/property state and allocation pointers | No |

These are selected qualified fields, not a complete structure declaration.
Sources: slot handler `4201DC70`, boot dispatcher `4201DF80`, announcement
handler `420473A8`, initializer `42023F84`, deadline helper `420400E0`, and
[the retained-descriptor trace](STOCK_HUB_POSTBOOT_TRACE.md).

Three different quantities must not be conflated:

1. **Software version:** association byte `+14`, updated from native `01`.
2. **DevVers:** separate slot **3**, a 40-entry per-address version table used
   for app/configuration reconciliation. New controller admission initializes
   its entry to **1** on the ordinary, non-replacement path.
3. **Shared transmit sequence:** RAM byte `3FCA710F`, generated by `42037920`
   and represented by six wire bits. It is neither the `+14` version nor the
   slot-3 version table.

### Durability is conditional on successful storage

`420ADFA4` sends type-9 writes to the blob setter `420EBB78`, then calls commit
`420EBB24`; failures return an error. `4201DC70` nevertheless copies the full
record into RAM after the write attempt. Thus a record may work in the current
session while a failed storage operation prevents equivalent recovery after
restart. This is a stock-code failure possibility, not evidence that it
occurred in our installation. Power-loss atomicity was not established.

## Lifecycle paths

### New association: pending first, persistent later

`420473A8` parses native `01`, checks admission and destination, and allocates
a candidate for an unknown sender. Its 52-byte association prefix is copied
into a pending-list entry with a separate deadline. This path is distinct
from committing the candidate to slot 4.

Controller-report handler `4204D658` subsequently looks up the pending sender
through `4203BD20`. When found, it initializes the ordinary slot-3 entry to
one, copies the 52-byte candidate prefix, removes the pending entry,
initializes model/port state, and calls `4201DF80(1,4,record)`. The no-candidate
branch loads the existing record instead. The same report handler can return
the slot-3 version in its ACK when the report requests it; that is not a
command-sequence reset.

This establishes a controller-report promotion boundary. It does not claim
that every device class uses native `02`, that every historical white flash
reached this boundary, or that promotion proves successful valve control.

### Known-device rejoin: retained assignment

In `420473A8`, lookup by the announced identity finds an existing slot-4
record. The branch checks device class and accepts the current hub destination,
zero destination, or its qualified migration condition. Selector helper
`42040410(1,...)` retains a nonzero `record+27`; it allocates a selector only
when that stored value is zero. The reply uses the retained address.

The handler compares incoming software version with `record+14`, records a
change, clears runtime bytes `+113/+114` on the successful rejoin branch,
and persists association updates when its migration/update conditions apply.
This is evidence for **responding to a recognized announcement without
discarding its association**, not for remotely waking a silent device.

The [HTV213 battery-cycle capture](HTV213_STOCK_CAPTURE_FINDINGS_20260928.md)
corroborates this distinction on hardware: with hub pairing not armed, boot
announcements received a retained assignment, followed by per-port state,
settings and plan exchanges and a successful bounded control. This validates
that observed stock-model path, not HCS026 wake behavior or our implementation.

An additional helper, `42038994`, modifies the runtime 64-bit field at `+104`
for device class `0x50`, depending on software version and its force argument.
It is not the shared sequence byte, lies outside the persisted 52-byte prefix,
and must not be treated as a generic counter reset or HCS026 recovery rule.

### Hub restart: load the association, rebuild runtime state

The slot-4 boot branch in `4201DF80` reads up to 40 association blobs into the
184-byte-stride table. For occupied slots it fills a missing model timing
default, loads model descriptors, invokes class-specific initialization, and
derives a runtime migration flag from the saved prefix. It does not load the
saved record as a complete live state machine or restore its old pointers.

The shared sequence is covered by the independently verified early boot
zero-fill, but startup traffic also consumes the generator. Consequently,
**saved association survives hub restart** is compatible with **transmit
sequence starts afresh at one initialization stage**. Neither proves the
first subsequent valve command should use a particular number, nor what a
battery-restarted valve expects. See [boot qualification](STOCK_HUB_BOOT_STATE_REFERENCE.md)
and [post-boot consumption](STOCK_HUB_POSTBOOT_TRACE.md).

### Delete, offline, and incomplete-admission cleanup are different

Explicit slot-4 deletion in `4201DC70` removes associated slot-10 data through
`4201DC08`, deletes the association KV key, releases descriptor/model/port
allocations, and zeroes all **184** RAM bytes (`4201DEE5..4201DEF1`). The RAM
clear occurs even if the key deletion reported failure. Slot-10 handler
`4201C374` is a separately keyed per-address store/cache, not the shared phase
generator.

App `DevVers` processing in `4200D7E4` uses zero/missing version entries to
remove local records, and requests refresh for changed nonzero entries.
Its outer helpers include clearing references to the removed address from
other runtime records (`42040768`, offsets `+54/+55`) and emitting an internal
event (`42027BA0`, event `0x53`). The inspected `4204E938` helper only logs.
The downstream event consumer and all computed callbacks were not traced
here: **these observations do not prove that deleting a device from the app
is radio-silent or erases the device's own pairing**.

Ordinary deadline-based offline handling retains the association, as qualified
in [the offline-state trace](STOCK_HUB_OFFLINE_RECOVERY_STATE.md). A separate
branch at the start of `420510C4` checks a global deadline and platform state,
then reconciles incomplete additions. Among its deletion conditions is a
nonvirtual entry with version **1** and a false `4203FDCC` predicate; it deletes
slot 4 and clears the corresponding version. Its diagnostic identifies failed
platform addition. The timer duration, every admission predicate and whether
this condition affected a historical device are not established by this pass.
Do not explain that branch as an ordinary missed-ACK timeout.

## Additional sequence consumers and reset limits

The retained direct-call references to generator `42037920` comprise three
qualified callers:

| Caller / call site | Bounded effect |
| --- | --- |
| Master-header builder `4203A344` / `4203A435` | Consumes a sequence while building a request, before RF acceptance. Controls, notifications and conditional forwarding reach this builder. |
| OOK/time sender `4204F940` / `4204FC03` | Under its enable/connection/mode gates, consumes a sequence before constructing a mode-4 transport through `42037F30` and queuing it with `4203A684`. |
| Gateway-property sender `4204DD6C` / `4204DE68` | Builds native `75` using a fresh sequence and queues matching through `4204A8E0`; reached from native-`73` factory-test handling. Builder failure still follows generation. |

The OOK/time sender is also called from master-control path `4204FCAC`.
This creates a concrete **conditional** reason for a shared sequence to advance
before the valve-control header itself. It does not establish that the OOK
feature was enabled during any of our captures.

The OOK sender's nearby increment/reset is a different byte: literal
`42041774` resolves to **`3FCA7109`**, while the command generator uses
**`3FCA710F`**. Its reset after the bounded OOK-send cycle is therefore not a
reset of the shared command sequence. Its scheduling deadline is separately
at `3FCA7120`. Independent decoding confirms the generator call and distinct
byte writes at `4204FC03` and `4204FC5F..4204FC71`.

No sequence persistence/restore, elapsed-time reset, special recovery command,
or rejection-driven sequence reset was established in these bounded paths.
This extends the [ACK/retry analysis](STOCK_HUB_ACK_RETRY_LIFECYCLE.md), not a
whole-firmware absence proof. Indirect aliases and untraced consumers remain
possible. Hub-generated sequences do not reveal the valve's acceptance state.

## Consequences for our implementation and tests

- Preserve durable association identity, owner and selector across service/node
  restart; rebuild transient deadlines/queues independently. Do not clear an
  association merely because telemetry becomes stale.
- Keep initial admission, known rejoin, status ACK, and control confirmation as
  separate states. Rejoin must not silently create a new logical device or
  reset unrelated command state.
- Add failure-injection coverage for persistence errors: an in-memory success
  must not be presented as durable enrollment without a successful save.
- Keep software version, configuration version and command phase explicitly
  named and independently tested. A configuration version of one is not
  evidence for a command counter of one.
- Test restart with the same identity/selector and known-announcement recovery
  without a new pairing window. Offline replay can validate our decisions;
  proving valve battery retention still needs a separately observed battery
  cycle. No additional valve actuation is justified by this note alone.

These are bounded design/test implications, not new implemented behavior or
an alternate task list; scheduling belongs in the canonical roadmap.

## Native assignment construction contract

September 29 follow-up: primary handler `420473A8`, its independently decoded
instructions, clock helper `4203B294`, and the
[HTV213 lifecycle capture](HTV213_STOCK_CAPTURE_FINDINGS_20260928.md) establish
the following **source-only, model-qualified** contract. It is not permission
to enable a transmitter or a claim that local retained rejoin is qualified.

### Request identity and model qualification

In the captured eight-byte HTV213 native `01` body:

| Data offset | Captured retained value | Qualified meaning |
| --- | --- | --- |
| `0` | `0b` | Announcement's reply/listen selector; passed separately to response transport |
| `1` | `ff` | Extended model/class encoding discriminator |
| `2` | `20` | Device class |
| `3..4` | `05 01` | Little-endian model code `0105` / 261 |
| `5` | `04` | Additional descriptor byte copied into the pending-candidate prefix; full semantics unresolved, **not established as port count** |
| `6` | `3e` | Reported software-version byte, 62, compared with association `+14` |
| `7` | `03` | Captured retained-boot value; complete bit semantics unresolved |

The fresh HTV213 example is `0c ff 20 05 01 04 3e 05`. Its changed selector and
last byte do not justify a universal boot-versus-pairing flag rule. The handler
parses class/model/descriptor/software at `42047420..42047490`; its known-record
branch checks identity, class and acceptable destination. A local implementation
should additionally require the saved qualified model and expected length, and
keep unknown descriptor/last-byte variants gated rather than treating any
native `01` as a supported valve. Software-version updates are separate from
configuration revisions; a new version is not a new device identity.

Incoming native `P[1..4]` is the destination checked against the current hub or
zero; `P[5..8]` is the announced device identity looked up by `4203B080`.
Foreign-hub migration requires the additional retained-record condition already
documented above. An offline timeout alone does not authorize that migration.
Use saved association routing, not installation-default identities or a generic
reversal of the broadcast request. The public fixture's synthetic normalized
endpoints must not be mistaken for native IDs without the one-bit conversion.

### Eleven-byte `81` body, with the observed header branch

For the captured valves, native request `P[9] & 0x40` is zero. The serializer
therefore reserves data byte 0 for status and writes this layout:

| Data offset | Meaning and source | HTV213 retained example |
| --- | --- | --- |
| `0` | Connection result: known-record branch `00`; ordinary new-candidate branch `0a` | `00` |
| `1` | Assigned **device address**, record `+0`; independent of port count | `02` |
| `2` | Retained/allocated RF selector, record `+27`, through `42040410` | `0b` |
| `3..4` | Little-endian model heartbeat interval from record `+30..31` | `e0 01` = 480 |
| `5..8` | Current packed local date/time, little-endian `T4` | Generated, never replayed from a fixture |
| `9` | Local weekday from the clock helper | Monday `01` in these captures |
| `10` | Configuration revision: saved slot-3 entry for known address; `01` on ordinary new admission | `02` |

Address/selector/timing stores are at `42047855..4204787C`; the heartbeat value
originates in model helper `4203FF60`, whose default is 480 seconds with
configuration-dependent overrides. Time/weekday serialization is
`4204787F..420478D5`; version selection is independently decoded at
`420478F3..42047935`. The observed address happens to equal this model's two
ports; **do not derive it from port count**, which is separately record `+28`.
The final byte is neither software version nor command sequence. This 11-byte
valve body contains no separately identified unit field; byte 9 is weekday,
not units. Native `02` ACK unit extensions are a different operation.

Header flag `P[9] & 0x40` selects an alternate serializer branch with no status
prefix, shifting these fields left and yielding ten base bytes. That branch
was not exercised by the HTV213 lifecycle capture. The class-47/48 sensor
extension adds five relay-related bytes after the revision; it must not leak
into a valve builder. Initially reject unqualified flags/classes rather than
silently applying the eleven-byte layout to every announcement.

### Clock and phase are not opaque replay fields

Independent S3 decoding of `4203B294` establishes the native `T4` bit layout:

```text
bits  0..5   second
bits  6..11  minute
bits 12..16  hour
bits 17..21  day
bits 22..25  month (1-based)
bits 26..31  year minus 2020
```

Anchors: day/hour `4203B2D6..4203B2E5`, minute/second
`4203B2ED..4203B2FF`, month/year `4203B304..4203B326`, little-endian output
`4203B340..4203B355`. The weekday copy at `4203B338..4203B33A` reads calendar
structure offset 24. Underlying calendar conversion `4211556C` computes a
normalized modulo-seven weekday at `421155E3..42115608`: **Sunday 0 through
Saturday 6**, consistent with the captured Monday value. Calendar validity and
2020–2083 bounds should be checked locally; do not duplicate the stock mask's
silent six-bit year wrapping. The existing normalized DOS-like helper is a
different representation, not bytes that can be inserted unchanged into `T4`.

The common reply-header builder `4203A4FC`, called at `42051CEA`, echoes the
request's full six-bit phase and sets native response command `81`. It does
not consume a new master-control sequence. Captured retained replies echo
phases 1 and 4; accepting one of them does not prove completion of subsequent
state/settings/plan exchanges or reset the command generator.

### Reply carrier is distinct from the returned assignment

Handler `420473A8` retains incoming data byte 0 in `uStack_40`; its call at
`42047ACE..42047ADA` passes that value to transport wrapper `42037ECC`, which
stores it in transport context byte `+3`. This is separate from the selector
written in `81` data byte 2. Fresh HTV213 requests advertise selector 12 and
receive assignments on approximately **434.35 MHz**, even while assigned
selectors vary. Retained requests advertise 11 and receive the reply near
**434.24 MHz**, also retaining assignment 11. Factory announcement sweep RX,
assignment TX and subsequent routine channel are therefore separate inputs.
Do not choose initial reply frequency only from the saved routine selector;
use a qualified request-selector mapping and preserve waveform qualification.

### Model differences and implementation boundary

Public fresh-assignment fixtures for HTV145 class `1f`/model `012e` and HTV405
class `26`/model `0026` share the eleven-byte envelope, but their addresses,
selectors and software bytes differ. Their captured replies begin `0a` and
end with revision 1. That establishes serializer overlap, not retained-rejoin
RF qualification for those models. Existing working HTV145/HTV405 fresh
prefixes should remain unchanged; HTV213's captured two-port `02/05/06` tail
is not a universal fixed eighteen-step sequence.

There is sufficient evidence for a pure retained-assignment body builder with
explicit saved address, selector, heartbeat seconds, configuration revision,
current local clock and weekday, plus a validated request phase/model context.
There is **not** evidence to invent missing persisted fields, enable unknown
selectors/header flags, or share one model's measured assignment timing with
another. A saved-association coordinator can remain disabled until a qualified
profile supplies those fields and RF settings. Qualification still requires
addressed per-port progress and confirmed control on dry hardware, not just a
locally generated assignment or retained UI record. No new runtime behavior is
claimed by this construction contract.
